# 08-adr.md · 架构决策记录

> 只在出现「二选一」的架构取舍时记录。当前已决策条目见 §3，待复核见 §5。

## 1. 机制

- **何时必须写**：框架选型、工程结构、存储方案、外部数据源、打包与分发、界面方案等跨模块取舍。
- **每条骨架**：标题 + 状态 + 日期 + 背景 + 决策 + **备选方案** + 后果。
- **备选方案段强制**：逐个记录真实备选及落败原因；不写「它击败了什么」，等于邀请后来者翻案。历史备选无法重建时如实标注。
- **生命周期**：`proposed` → `accepted` / `rejected`（状态行写一行否决原因）；被取代标 `superseded` 并指向新条目。`rejected` / `superseded` 默认保留；防翻案价值消失且经用户确认后才可清理，并在修订记录留痕。
- **分工**：需求侧否决（不做什么）记在 `docs/REQUIREMENTS.md` 或 00 范围边界；方案侧否决（怎么做被否决）记在本文件，一类否决只记一处。
- **事实同步**：后续改动使 ADR 中的路径、名称、默认值过时，同批修正事实，不改决策本身。
- **事故复盘【可选】**：影响面大的踩坑可独立成篇，记录时间线、根因、纠正项与回归护栏；纠正项转成硬约束或 ADR 后在此留链接。

## 2. ADR 模板

```markdown
### ADR-NNN 标题

- 日期：YYYY-MM-DD
- 背景：要解决什么问题，约束是什么
- 决策：选了什么，边界在哪里
- 备选方案：
  - 方案 A：……；落败原因：……
  - 方案 B：……；落败原因：……
- 后果：需要配套改动什么，引入什么风险，何时复查
```

## 4. ADR 正文

### ADR-001 技术选型：Tauri 2 + React 19.3.1 + TypeScript 6.0.3 + Ant Design 6.6.7

- 状态：accepted
- 日期：2026-10-24
- 背景：产品要求安装包轻、启动快、内存低；同时需要绝对路径拖拽、剪贴板文件、SQLite、系统缩略图、打开/定位原文件。用户明确选择 React，并要求依赖使用最新稳定版。
- 决策：桌面壳 Tauri 2；前端 React 19.3.1 + TypeScript 6.0.3 + Ant Design 6.6.7；Vite 8.3.5 构建；Rust 负责平台能力与持久化；Windows 优先；**纯桌面客户端，不生成 iOS/Android 目标，不保留移动端图标或 `mobile_entry_point`**。
- 备选方案：
  - Vue 3.5 + Element Plus：用户明确改为 React + Ant Design；否决。
  - Electron + React：原生能力最全，但安装包与启动开销不符合「轻量」目标；保留为 Tauri 不可行时的兜底。
  - 本地 Web + 浏览器：浏览器拿不到拖拽文件的绝对路径，剪贴板文件也受限；否决。
  - Tauri 1：v2 已稳定，插件与权限模型更完整；否决。
- 后果：需要维护小型 Rust 平台层；剪贴板文件路径需用 `clipboard-win` 补 `CF_HDROP`；缩略图需调用 Windows Shell；WebView2 随系统或安装器提供。M0 必须先做剪贴板文件与画布 spike。
- 版本基线：React / React DOM 19.3.1、Ant Design 6.6.7、`@ant-design/icons` 6.3.4、Vite 8.3.5、`@vitejs/plugin-react` 6.1.2、TypeScript 6.0.3。TypeScript 7.0.2 与 `typescript-eslint` 8.72 的 peer 上限 `<6.1.0` 冲突，暂不使用。

### ADR-002 工程结构：单体单应用

- 状态：accepted
- 日期：2026-10-24
- 背景：v1 是单窗口桌面应用，团队规模小，优先跑通与可维护；没有多端复用需求。
- 决策：单体单应用，目录为 `desktop/` + `client/` + `docs/`；Rust 平台层在 `desktop`，前端领域命令与编排当前在 `client/workspace`；`client/domain`、`client/shared` 为规划目录，尚未创建。
- 备选方案：
  - Monorepo 拆包：未来多端时有利，但当前增加构建与依赖管理成本；否决。
  - 单文件/少目录：无法承载画布、领域、平台三层；否决。
- 后果：领域命令目前以 hook 形式存在且可单测；未来若拆包，按 `domain / shared / client` 迁移，不得把业务规则写回组件。

### ADR-003 存储：SQLite + dataWorkSpace

- 状态：accepted
- 日期：2026-10-24
- 背景：需要关系查询、事务、搜索、崩溃恢复；粘贴截图需要本地资源目录；用户要求数据可迁移。
- 决策：SQLite（Rust `rusqlite`，WAL）+ `dataWorkSpace`；`dataWorkSpace` 内含 `ploceus.db`、`assets/`、`thumbnails/`；默认安装目录（可写）下，回退 Tauri `app_data_dir`，设置可迁移。
- 备选方案：
  - JSON 文件：全量读写、损坏风险、查询弱；否决。
  - IndexedDB：数据在浏览器存储，不符合「本地工作空间可迁移」；否决。
  - 云端数据库：违反纯本地约束；否决。
- 后果：SQLite 跟随 Rust 编译；工作空间迁移需要复制-校验-切换；不做复杂容灾，损坏时重建并重新导入。

### ADR-004 外部数据源：纯本地

- 状态：accepted
- 日期：2026-10-24
- 背景：产品处理个人文件与工作材料，隐私敏感；用户明确不做云端。
- 决策：不接模型 API、不做遥测、不抓取网页；URL 只交给系统浏览器打开；缩略图只在本地生成。
- 备选方案：
  - 接 AI 分类/摘要：增加隐私与依赖，且当前无需求；否决。
  - 云端同步：用户明确不做；否决。
- 后果：所有功能离线可用；未来若引入外部服务，必须新增 ADR 并显式开启。

### ADR-005 画布引擎：Konva 虚拟化渲染

- 状态：accepted（Konva + react-konva + rbush 已落地于 `CanvasBoard.tsx`）
- 日期：2026-10-24
- 背景：v1 先支持数千到一万节点，容量目标十万级；React Flow 的 DOM 节点在万级规模不可控。
- 决策：Konva 作为生产绘制层；场景数据在普通 TS store；首屏只加载紧凑场景索引，可见节点详情按需拉取；`rbush` 做视口空间索引；只创建可见节点的 Konva 形状；渲染按需。三档 LOD 已由 ADR-016 取消。旧 DOM 虚拟行实现（`FileTile.tsx`）已删除。
- 备选方案：
  - React Flow：开发最快，但 DOM 节点数量上限低，十万级不可行；否决。
  - PixiJS：WebGL 性能更好，但文字、编辑、命中与交互要自建，成本更高；否决。
  - 纯 Canvas 2D 自绘：控制力最强，但重复实现命中、变换、文本；否决。
- 后果：画布层工作量增加；需要显存与帧率基准；领域模型与画布解耦，后续仍可替换渲染层。1 万/10 万基准仍待实测（§5）。

### ADR-006 只读引用边界与 HC-12 改写

- 状态：accepted
- 日期：2026-10-24
- 背景：产品只管理文件地址，不搬运文件；旧 HC-12 要求所有文件操作限制在用户选定根目录，与新场景冲突。
- 决策：应用不得修改、移动、重命名、删除用户文件；读取、打开、定位仅限用户显式导入的引用；Rust 解析真实路径后校验，不跟随符号链接越界；打开/定位只接受 `refId`。
- 备选方案：
  - 保留根目录 + 整理器：用户明确推翻旧 v1；否决。
  - 允许任意路径打开：扩大攻击面与误操作风险；否决。
- 后果：HC-12 改写为「只读引用边界」；HC-10/11 在 v1 不触发；未来若增加文件操作，必须重新设计操作记录与撤销。

### ADR-007 文件级去重与定位优先

- 状态：accepted
- 日期：2026-10-24
- 背景：用户要求重复文件不重复出现；文字与截图去重成本高、易误判；定位是核心体验。
- 决策：只对文件/文件夹按规范化真实路径去重；`refs(kind, dedupe_key)` 只对 file/folder 建部分唯一索引，`nodes.ref_id` 唯一；重复导入返回已有节点并定位；文字、截图、URL 不去重。
- 备选方案：
  - 全部内容哈希去重：计算成本高，且相似截图/文字可能被误合并；否决。
  - 全部不去重：文件重复卡片会破坏空间索引；否决。
  - UI 层去重：约束不可靠，异常/批量导入会漏；否决。
- 后果：一个引用只有一张卡片；跨项目关系用连线/标注表达；定位逻辑复用于搜索与重复导入。

### ADR-008 窗口形态与渲染生命周期

- 状态：accepted
- 日期：2026-10-24
- 背景：用户希望参考桌面常驻工具的使用体感，但不希望后台常驻进程持续消耗资源；窗口缩小时搜索框必须可用。
- 决策：原生窗口边框（`decorations: true`）；内容区顶部搜索固定；桌面常驻为可选（默认关闭）；关闭即退出；最小化/隐藏/失焦暂停 RAF、动画与缩略图加载；无交互动画不重绘。（窗口形态经 ADR-011 → ADR-012，当前为 `decorations: false` 无边框自定义标题栏；紧凑模式取消。）
- 备选方案：
  - 托盘常驻 + 后台进程：不符合「不需要一直常住进程」；否决为默认。
  - 一直渲染：浪费 GPU/CPU；否决。
- 后果：需要窗口事件与画布生命周期联动；性能基准覆盖隐藏/恢复场景。

### ADR-009 Windows Shell 原生缩略图

- 状态：accepted
- 日期：2026-10-24
- 背景：用户要求文件、图片、EXE 等显示与资源管理器一致的缩略图/图标，不自建图标集。
- 决策：Windows 使用 `IShellItemImageFactory::GetImage` 获取缩略图，失败回退 `SHGetFileInfoW` 图标；剪贴板图片用 `image` crate；缩略图异步生成并缓存。
- 备选方案：
  - 自建扩展名图标表：无法覆盖 EXE、Office、视频等系统提供者；否决。
  - 只显示类型图标：不满足系统原生效果；否决。
  - Electron `nativeImage`：Tauri 无等价 API，且已选 Tauri；否决。
- 后果：需要 COM 初始化与独立线程；Windows 优先，macOS/Linux 后续补平台实现。

### ADR-010 高密度系统图标 UI

- 状态：superseded by ADR-013（窗口形态部分此前由 ADR-011/012 调整）
- 日期：2026-10-24
- 背景：用户明确否决大卡片与过度设计：几千个文件时大缩略图会挤占画布；要求直接使用系统图标、界面简单。
- 决策：默认 176×28 紧凑行；左侧 16px 系统风格图标，只显示单行文件名，路径通过 Tooltip 展示；默认缩放下同屏 120–200+ 行（随窗口尺寸）；低于 50% 降级为色点；分组只画 1px 虚线框；内容区顶部搜索常驻；不做渐变、玻璃拟态、大圆角。
- 备选方案：
  - 大缩略图卡片：视觉丰富但同屏只能放十几个，违反高密度目标；否决。
  - 自建图标集：与用户系统不一致，且无法覆盖 EXE/Office/视频；否决。
  - 装饰性面板/仪表盘布局：增加心智负担；否决。
- 后果：需要 `TitleBar`、`FileTile`、`SystemIcon` 与同屏计数；当前客户端用 React DOM 实现密度，M2 将渲染层切换到 Konva。

### ADR-011 原生窗口边框与去原型化

- 状态：superseded by ADR-012
- 日期：2026-10-24
- 背景：无边框方案需要在页面内自绘最小化/最大化/关闭按钮，并额外维护拖拽区与窗口权限；用户明确要求这些属于客户端能力，不应作为页面 UI 出现；同时要求删除原型目录，避免工程内维护第二套界面。
- 决策：`tauri.conf.json` 设 `decorations: true`，窗口控制交给 Windows 原生标题栏；删除 `TitleBar` 中的 logo、紧凑模式与窗口控制按钮，仅保留搜索、新建文字、设置；应用内容区铺满窗口，不再渲染"桌面里漂浮一扇窗口"的模拟外壳；删除 `prototypes/` 与相关引用。
- 备选方案：
  - 保留无边框 + 自绘按钮并补 `core:window:*` 权限：仍会把窗口能力放进页面 UI；否决。
  - 保留模拟桌面外壳：产生大片留白且与真实客户端不符；否决。
- 后果：窗口外观由系统决定；前端只负责内容；文档与命令表同步去除无边框、紧凑模式与原型条目。（窗口形态已被 ADR-012 推翻。）

### ADR-012 恢复无边框自定义标题栏与 F12 调试

- 状态：accepted
- 日期：2026-10-24
- 背景：用户要求 logo 回到标题栏、搜索绝对居中、最小化/最大化/关闭按钮可见且可用，并保留拖动窗口的客户端行为；同时要求 F12 能查看调试信息且不影响上线。
- 决策：`decorations: false`；标题栏左侧 logo + 名称，中间搜索绝对居中，右侧新建文字、设置与窗口按钮；标题栏空白处 `data-tauri-drag-region` 原生拖动；`capabilities/default.json` 显式授予 `start-dragging` / `minimize` / `toggle-maximize` / `close`；`tauri` 启用 `devtools` feature，新增 `open_devtools` 命令供 F12 调用。原型目录与紧凑模式保持删除。
- 备选方案：
  - 原生窗口边框：窗口按钮与拖动由系统提供，但无法满足 logo + 居中搜索的自定义标题栏；否决。
  - 仅用 CSS `-webkit-app-region: drag`：Tauri 2 不识别该属性；否决。
- 后果：窗口能力依赖显式权限，缺一条就会静默失效；`devtools` feature 会增大 release 包体，需要在打包验收时检查体积。

### ADR-013 Windows 桌面式高密度图标网格

- 状态：accepted
- 日期：2026-10-24
- 背景：长条文件行被用户否决；大量项目资料需要更接近 Windows 桌面的扫描方式，同时分组内固定高度产生了大片无意义空白。
- 决策：默认采用 72px 宽图标格，32px 系统图标在上、最多两行名称在下；默认透明，仅悬停与选中显示底色；空间按内容收高，禁止等高和预留空行；远景不降级为色点（见 ADR-016）。
- 备选方案：
  - 保留 176×28 紧凑行：信息密度高，但形态已被用户明确否决；不再作为默认形态。
  - 大缩略图卡片：适合图片浏览，但大量办公文件场景同屏数量过低；否决。
- 后果：`CanvasBoard` 已按目标规范落地；旧 176×28 紧凑行实现（`FileTile`）已删除；远景色点 LOD 已由 ADR-016 取消；验收增加同屏计数与分组空白检查。

### ADR-014 语义色令牌与可切换浅色主题

- 状态：accepted
- 日期：2026-10-24
- 背景：单一硬编码配色无法兼顾办公长时间使用与个人偏好；Ant Design 组件与 Konva 画布若分别配色会产生不一致。
- 决策：默认灰雾紫，提供石板蓝灰、青禾灰绿、石墨灰四套浅色主题；所有界面颜色通过语义令牌映射，Ant Design 与 Konva 共用主题快照；主题 ID 存入 `app_meta.ui_theme`，切换不改变场景与交互状态。暗色模式不在本次范围内。
- 备选方案：
  - 单一硬编码色板：实现最短，但无法切换且组件与画布容易漂移；否决。
  - 跟随系统自动反色/暗色：当前没有暗色设计，自动反色无法保证对比度与文件图标识别；否决。
- 后果：需要统一 React/Ant Design/Konva 的令牌映射与对比度验收；系统文件图标与错误/警告/成功语义不随主题重着色；标注文字牌与未自定义的空间/连线跟随主题主色（见 ADR-017）。

### ADR-015 分组模型：独立 `groups` 表 + `nodes.group_id`

- 状态：accepted
- 日期：2026-10-24
- 背景：v1 需要分组框组织项目，但节点坐标必须保持世界坐标（连线、标注、定位都按世界坐标计算）；分组框要能独立移动并带动内部节点。
- 决策：`groups(id, title, color, x, y, w, h)` 独立表，节点用 `group_id` 引用（空字符串 = 未分组）；移动分组时由应用层同步平移内部节点坐标；删除分组只清空归属，不删节点；对象拖入/拖出空间时按中心点自动更新归属（见 ADR-017）。
- 备选方案：
  - `type=frame` 节点 + `parent_node_id` 相对坐标：统一了模型，但所有坐标换算（连线、框选、定位、搜索）都要处理两级坐标，出错面大；否决。
  - 两套并存：短期灵活，长期两套语义互相打架；否决。
- 后果：`scene_save` 需维护分组差集清理与孤儿 `group_id` 归一；`z` / `parent_node_id` / `data_json` 字段已建但未启用，未来若做嵌套挂载再评估。

### ADR-016 取消远景 LOD，改为全量渲染 + 高清倍率

- 状态：accepted
- 日期：2026-10-25
- 背景：三档 LOD 在缩小后把对象降级为类型色点，用户无法辨认内容；同时低 DPI 屏上图元与文字边缘发虚，观感「不清晰」。
- 决策：取消远景色点与中景简化行，任何缩放都绘制完整图标格与名称；对象卡片高度按名称行数（最多两行）与标注自适应，不再固定 64px；`Konva.pixelRatio` 固定不低于 2；主题边框与次要文字整体提高对比度。
- 备选方案：
  - 保留色点但增加悬停提示：缩小后仍需逐个悬停才能辨认，效率低；否决。
  - 按缩放提高 pixelRatio：显存随缩放增长不可控；否决。
- 后果：低缩放时需要绘制的对象更多，依赖 rbush 视口裁剪兜底；1 万/10 万基准需重新测量显存与帧率。

### ADR-017 空间成员自动归属与空间/连线取色

- 状态：accepted
- 日期：2026-10-25
- 背景：空间创建后无法直观地把新对象加入或移出；多个空间与多条连线颜色相同，难以区分；空间标题只是占位文本。
- 决策：对象拖动结束后按中心点重算 `group_id`，进入空间即成为成员、离开即脱离；新对象落点已在空间内时同样自动归属。空间新增 `color` 字段，边框与内部浅色底由该色派生；连线颜色写入 `edges.style_json`。空间标题即空间标注，支持自动编号、重命名与双击编辑。右键提供取色器与「跳转到关联对象」。
- 备选方案：
  - 手动勾选成员：多一步操作且容易漏；否决。
  - 只在创建时分组：无法表达后续整理；否决。
- 后果：`groups` 增加 `color` 列，`SCHEMA_VERSION` 升到 2；拖动结束需要额外计算空间归属；取色器使用 Ant Design `ColorPicker`，初始包体增大。
