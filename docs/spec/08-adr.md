﻿# 08-adr.md · 架构决策记录

> 只在出现「二选一」的架构取舍时记录。当前已决策条目见 §3，待复核见 §5。

## 1. 机制

- **何时必须写**：框架选型、工程结构、存储方案、外部数据源、打包与分发、界面方案等跨模块取舍。
- **每条骨架**：标题 + 状态 + 日期 + 背景 + 决策 + **备选方案** + 后果。
- **备选方案段强制**：逐个记录真实备选及落败原因；不写「它击败了什么」，等于邀请后来者翻案。历史备选无法重建时如实标注。
- **生命周期**：`proposed` → `accepted` / `rejected`（状态行写一行否决原因）；被取代标 `superseded` 并指向新条目。`rejected` / `superseded` 默认保留；防翻案价值消失且经用户确认后才可清理，并在修订记录留痕。
- **分工**：需求侧否决（不做什么）记在 `docs/REQUIREMENTS.md` 或 00 范围边界；方案侧否决（怎么做被否决）记在本文件，一类否决只记一处。
- **事实同步**：后续改动使 ADR 中的路径、名称、默认值过时，同批修正事实，不改决策本身。
- **事故复盘【可选】**：影响面大的踩坑可独立成篇，记录时间线、根因、纠正项与回归护栏；纠正项转成硬约束或 ADR 后在此留链接。

## 2. ADR 模板

```markdown
### ADR-NNN 标题

- 状态：proposed / accepted / rejected / superseded
- 日期：YYYY-MM-DD
- 背景：要解决什么问题，约束是什么
- 决策：选了什么，边界在哪里
- 备选方案：
  - 方案 A：……；落败原因：……
  - 方案 B：……；落败原因：……
- 后果：需要配套改动什么，引入什么风险，何时复查
```

## 4. ADR 正文

### ADR-001 技术选型：Tauri 2 + React 19.3.1 + TypeScript 6.0.3 + Ant Design 6.6.7

- 状态：accepted
- 日期：2026-10-24
- 背景：产品要求安装包轻、启动快、内存低；同时需要绝对路径拖拽、剪贴板文件、SQLite、系统缩略图、打开/定位原文件。用户明确选择 React，并要求依赖使用最新稳定版。
- 决策：桌面壳 Tauri 2；前端 React 19.3.1 + TypeScript 6.0.3 + Ant Design 6.6.7；Vite 8.3.5 构建；Rust 负责平台能力与持久化；Windows 优先；**纯桌面客户端，不生成 iOS/Android 目标，不保留移动端图标或 `mobile_entry_point`**。
- 备选方案：
  - Vue 3.5 + Element Plus：用户明确改为 React + Ant Design；否决。
  - Electron + React：原生能力最全，但安装包与启动开销不符合「轻量」目标；保留为 Tauri 不可行时的兜底。
  - 本地 Web + 浏览器：浏览器拿不到拖拽文件的绝对路径，剪贴板文件也受限；否决。
  - Tauri 1：v2 已稳定，插件与权限模型更完整；否决。
- 后果：需要维护小型 Rust 平台层；剪贴板文件路径需用 `clipboard-win` 补 `CF_HDROP`；缩略图需调用 Windows Shell；WebView2 随系统或安装器提供。M0 必须先做剪贴板文件与画布 spike。
- 版本基线：React / React DOM 19.3.1、Ant Design 6.6.7、`@ant-design/icons` 6.3.4、Vite 8.3.5、`@vitejs/plugin-react` 6.1.2、TypeScript 6.0.3。TypeScript 7.0.2 与 `typescript-eslint` 8.72 的 peer 上限 `<6.1.0` 冲突，暂不使用。

### ADR-002 工程结构：单体单应用

- 状态：accepted
- 日期：2026-10-24
- 背景：v1 是单窗口桌面应用，团队规模小，优先跑通与可维护；没有多端复用需求。
- 决策：单体单应用，目录为 `desktop/` + `client/` + `docs/`；Rust 平台层在 `desktop`，前端领域命令与编排当前在 `client/workspace`；`client/domain`、`client/shared` 为规划目录，尚未创建。
- 备选方案：
  - Monorepo 拆包：未来多端时有利，但当前增加构建与依赖管理成本；否决。
  - 单文件/少目录：无法承载画布、领域、平台三层；否决。
- 后果：领域命令目前以 hook 形式存在且可单测；未来若拆包，按 `domain / shared / client` 迁移，不得把业务规则写回组件。

### ADR-003 存储：SQLite + dataWorkSpace

- 状态：accepted
- 日期：2026-10-24
- 背景：需要关系查询、事务、搜索、崩溃恢复；粘贴截图需要本地资源目录；用户要求数据可迁移。
- 决策：SQLite（Rust `rusqlite`，WAL）+ `dataWorkSpace`；`dataWorkSpace` 内含 `ploceus.db`、`assets/`、`thumbnails/`；默认安装目录（可写）下，回退 Tauri `app_data_dir`，设置可迁移。
- 备选方案：
  - JSON 文件：全量读写、损坏风险、查询弱；否决。
  - IndexedDB：数据在浏览器存储，不符合「本地工作空间可迁移」；否决。
  - 云端数据库：违反纯本地约束；否决。
- 后果：SQLite 跟随 Rust 编译；工作空间迁移需要复制-校验-切换；不做复杂容灾，损坏时重建并重新导入。

### ADR-004 外部数据源：纯本地

- 状态：accepted
- 日期：2026-10-24
- 背景：产品处理个人文件与工作材料，隐私敏感；用户明确不做云端。
- 决策：不接模型 API、不做遥测、不抓取网页；URL 只交给系统浏览器打开；缩略图只在本地生成。
- 备选方案：
  - 接 AI 分类/摘要：增加隐私与依赖，且当前无需求；否决。
  - 云端同步：用户明确不做；否决。
- 后果：所有功能离线可用；未来若引入外部服务，必须新增 ADR 并显式开启。

### ADR-005 画布引擎：Konva 虚拟化渲染

- 状态：accepted（Konva + react-konva + rbush 已落地于 `CanvasBoard.tsx`）
- 日期：2026-10-24
- 背景：v1 先支持数千到一万节点，容量目标十万级；React Flow 的 DOM 节点在万级规模不可控。
- 决策：Konva 作为生产绘制层；场景数据在普通 TS store；首屏只加载紧凑场景索引，可见节点详情按需拉取；`rbush` 做视口空间索引；只创建可见节点的 Konva 形状；渲染按需。三档 LOD 已由 ADR-016 取消。旧 DOM 虚拟行实现（`FileTile.tsx`）已删除。
- 备选方案：
  - React Flow：开发最快，但 DOM 节点数量上限低，十万级不可行；否决。
  - PixiJS：WebGL 性能更好，但文字、编辑、命中与交互要自建，成本更高；否决。
  - 纯 Canvas 2D 自绘：控制力最强，但重复实现命中、变换、文本；否决。
- 后果：画布层工作量增加；需要显存与帧率基准；领域模型与画布解耦，后续仍可替换渲染层。1 万/10 万基准仍待实测（§5）。

### ADR-006 只读引用边界与 HC-12 改写

- 状态：accepted
- 日期：2026-10-24
- 背景：产品只管理文件地址，不搬运文件；旧 HC-12 要求所有文件操作限制在用户选定根目录，与新场景冲突。
- 决策：应用不得修改、移动、重命名、删除用户文件；读取、打开、定位仅限用户显式导入的引用；Rust 解析真实路径后校验，不跟随符号链接越界；打开/定位只接受 `refId`。
- 备选方案：
  - 保留根目录 + 整理器：用户明确推翻旧 v1；否决。
  - 允许任意路径打开：扩大攻击面与误操作风险；否决。
- 后果：HC-12 改写为「只读引用边界」；HC-10/11 在 v1 不触发；未来若增加文件操作，必须重新设计操作记录与撤销。

### ADR-007 文件级去重与定位优先

- 状态：accepted
- 日期：2026-10-24
- 背景：用户要求重复文件不重复出现；文字与截图去重成本高、易误判；定位是核心体验。
- 决策：只对文件/文件夹按规范化真实路径去重；`refs(kind, dedupe_key)` 只对 file/folder 建部分唯一索引，`nodes.ref_id` 唯一；重复导入返回已有节点并定位；文字、截图、URL 不去重。
- 备选方案：
  - 全部内容哈希去重：计算成本高，且相似截图/文字可能被误合并；否决。
  - 全部不去重：文件重复卡片会破坏空间索引；否决。
  - UI 层去重：约束不可靠，异常/批量导入会漏；否决。
- 后果：一个引用只有一张卡片；跨项目关系用连线/标注表达；定位逻辑复用于搜索与重复导入。

### ADR-008 窗口形态与渲染生命周期

- 状态：accepted
- 日期：2026-10-24
- 背景：用户希望参考桌面常驻工具的使用体感，但不希望后台常驻进程持续消耗资源；窗口缩小时搜索框必须可用。
- 决策：原生窗口边框（`decorations: true`）；内容区顶部搜索固定；桌面常驻为可选（默认关闭）；关闭即退出；最小化/隐藏/失焦暂停 RAF、动画与缩略图加载；无交互动画不重绘。（窗口形态经 ADR-011 → ADR-012，当前为 `decorations: false` 无边框自定义标题栏；紧凑模式取消。）
- 备选方案：
  - 托盘常驻 + 后台进程：不符合「不需要一直常住进程」；否决为默认。
  - 一直渲染：浪费 GPU/CPU；否决。
- 后果：需要窗口事件与画布生命周期联动；性能基准覆盖隐藏/恢复场景。

### ADR-009 Windows Shell 原生缩略图

- 状态：accepted
- 日期：2026-10-24
- 背景：用户要求文件、图片、EXE 等显示与资源管理器一致的缩略图/图标，不自建图标集。
- 决策：Windows 使用 `IShellItemImageFactory::GetImage` 获取缩略图，失败回退 `SHGetFileInfoW` 图标；剪贴板图片用 `image` crate；缩略图异步生成并缓存。
- 备选方案：
  - 自建扩展名图标表：无法覆盖 EXE、Office、视频等系统提供者；否决。
  - 只显示类型图标：不满足系统原生效果；否决。
  - Electron `nativeImage`：Tauri 无等价 API，且已选 Tauri；否决。
- 后果：需要 COM 初始化与独立线程；Windows 优先，macOS/Linux 后续补平台实现。

### ADR-010 高密度系统图标 UI

- 状态：superseded by ADR-013（窗口形态部分此前由 ADR-011/012 调整）
- 日期：2026-10-24
- 背景：用户明确否决大卡片与过度设计：几千个文件时大缩略图会挤占画布；要求直接使用系统图标、界面简单。
- 决策：默认 176×28 紧凑行；左侧 16px 系统风格图标，只显示单行文件名，路径通过 Tooltip 展示；默认缩放下同屏 120–200+ 行（随窗口尺寸）；低于 50% 降级为色点；分组只画 1px 虚线框；内容区顶部搜索常驻；不做渐变、玻璃拟态、大圆角。
- 备选方案：
  - 大缩略图卡片：视觉丰富但同屏只能放十几个，违反高密度目标；否决。
  - 自建图标集：与用户系统不一致，且无法覆盖 EXE/Office/视频；否决。
  - 装饰性面板/仪表盘布局：增加心智负担；否决。
- 后果：需要 `TitleBar`、`FileTile`、`SystemIcon` 与同屏计数；当前客户端用 React DOM 实现密度，M2 将渲染层切换到 Konva。

### ADR-011 原生窗口边框与去原型化

- 状态：superseded by ADR-012
- 日期：2026-10-24
- 背景：无边框方案需要在页面内自绘最小化/最大化/关闭按钮，并额外维护拖拽区与窗口权限；用户明确要求这些属于客户端能力，不应作为页面 UI 出现；同时要求删除原型目录，避免工程内维护第二套界面。
- 决策：`tauri.conf.json` 设 `decorations: true`，窗口控制交给 Windows 原生标题栏；删除 `TitleBar` 中的 logo、紧凑模式与窗口控制按钮，仅保留搜索、新建文字、设置；应用内容区铺满窗口，不再渲染"桌面里漂浮一扇窗口"的模拟外壳；删除 `prototypes/` 与相关引用。
- 备选方案：
  - 保留无边框 + 自绘按钮并补 `core:window:*` 权限：仍会把窗口能力放进页面 UI；否决。
  - 保留模拟桌面外壳：产生大片留白且与真实客户端不符；否决。
- 后果：窗口外观由系统决定；前端只负责内容；文档与命令表同步去除无边框、紧凑模式与原型条目。（窗口形态已被 ADR-012 推翻。）

### ADR-012 恢复无边框自定义标题栏与 F12 调试

- 状态：accepted
- 日期：2026-10-24
- 背景：用户要求 logo 回到标题栏、搜索绝对居中、最小化/最大化/关闭按钮可见且可用，并保留拖动窗口的客户端行为；同时要求 F12 能查看调试信息且不影响上线。
- 决策：`decorations: false`；标题栏左侧 logo + 名称，中间搜索绝对居中，右侧新建文字、设置与窗口按钮；标题栏空白处 `data-tauri-drag-region` 原生拖动；`capabilities/default.json` 显式授予 `start-dragging` / `minimize` / `toggle-maximize` / `close`；`tauri` 启用 `devtools` feature，新增 `open_devtools` 命令供 F12 调用。原型目录与紧凑模式保持删除。
- 备选方案：
  - 原生窗口边框：窗口按钮与拖动由系统提供，但无法满足 logo + 居中搜索的自定义标题栏；否决。
  - 仅用 CSS `-webkit-app-region: drag`：Tauri 2 不识别该属性；否决。
- 后果：窗口能力依赖显式权限，缺一条就会静默失效；`devtools` feature 会增大 release 包体，需要在打包验收时检查体积。

### ADR-013 Windows 桌面式高密度图标网格

- 状态：accepted
- 日期：2026-10-24
- 背景：长条文件行被用户否决；大量项目资料需要更接近 Windows 桌面的扫描方式，同时分组内固定高度产生了大片无意义空白。
- 决策：默认采用 72px 宽图标格，32px 系统图标在上、最多两行名称在下；默认透明，仅悬停与选中显示底色；空间按内容收高，禁止等高和预留空行；远景不降级为色点（见 ADR-016）。
- 备选方案：
  - 保留 176×28 紧凑行：信息密度高，但形态已被用户明确否决；不再作为默认形态。
  - 大缩略图卡片：适合图片浏览，但大量办公文件场景同屏数量过低；否决。
- 后果：`CanvasBoard` 已按目标规范落地；旧 176×28 紧凑行实现（`FileTile`）已删除；远景色点 LOD 已由 ADR-016 取消；验收增加同屏计数与分组空白检查。

### ADR-014 语义色令牌与可切换浅色主题

- 状态：accepted
- 日期：2026-10-24
- 背景：单一硬编码配色无法兼顾办公长时间使用与个人偏好；Ant Design 组件与 Konva 画布若分别配色会产生不一致。
- 决策：默认灰雾紫，提供石板蓝灰、青禾灰绿、石墨灰四套浅色主题；所有界面颜色通过语义令牌映射，Ant Design 与 Konva 共用主题快照；主题 ID 存入 `app_meta.ui_theme`，切换不改变场景与交互状态。暗色模式不在本次范围内。
- 备选方案：
  - 单一硬编码色板：实现最短，但无法切换且组件与画布容易漂移；否决。
  - 跟随系统自动反色/暗色：当前没有暗色设计，自动反色无法保证对比度与文件图标识别；否决。

### ADR-015 分组模型：独立 `groups` 表 + `nodes.group_id`

- 状态：accepted
- 日期：2026-10-24
- 背景：v1 需要分组框组织项目，但节点坐标必须保持世界坐标（连线、标注、定位都按世界坐标计算）；分组框要能独立移动并带动内部节点。
- 决策：`groups(id, title, color, x, y, w, h)` 独立表，节点用 `group_id` 引用（空字符串 = 未分组）；移动分组时由应用层同步平移内部节点坐标；删除分组只清空归属，不删节点；对象拖入/拖出空间时按中心点自动更新归属（见 ADR-017）。
- 备选方案：
  - `type=frame` 节点 + `parent_node_id` 相对坐标：统一了模型，但所有坐标换算（连线、框选、定位、搜索）都要处理两级坐标，出错面大；否决。
  - 两套并存：短期灵活，长期两套语义互相打架；否决。
- 后果：`scene_save` 需维护分组差集清理与孤儿 `group_id` 归一；`z` / `parent_node_id` / `data_json` 字段已建但未启用，未来若做嵌套挂载再评估。

### ADR-016 取消远景 LOD，改为全量渲染 + 高清倍率

- 状态：accepted
- 日期：2026-10-25
- 背景：三档 LOD 在缩小后把对象降级为类型色点，用户无法辨认内容；同时低 DPI 屏上图元与文字边缘发虚，观感「不清晰」。
- 决策：取消远景色点与中景简化行，任何缩放都绘制完整图标格与名称；对象卡片高度按名称行数（最多两行）与标注自适应，不再固定 64px；`Konva.pixelRatio` 固定不低于 2；主题边框与次要文字整体提高对比度。
- 备选方案：
  - 保留色点但增加悬停提示：缩小后仍需逐个悬停才能辨认，效率低；否决。
  - 按缩放提高 pixelRatio：显存随缩放增长不可控；否决。
- 后果：低缩放时需要绘制的对象更多，依赖 rbush 视口裁剪兜底；1 万/10 万基准需重新测量显存与帧率。

### ADR-017 空间成员自动归属与空间/连线取色

- 状态：accepted
- 日期：2026-10-25
- 背景：空间创建后无法直观地把新对象加入或移出；多个空间与多条连线颜色相同，难以区分；空间标题只是占位文本。
- 决策：对象拖动结束后按中心点重算 `group_id`，进入空间即成为成员、离开即脱离；新对象落点已在空间内时同样自动归属。空间新增 `color` 字段，边框与内部浅色底由该色派生；连线颜色写入 `edges.style_json`。空间标题即空间标注，支持自动编号、重命名与双击编辑。右键提供取色器与「跳转到关联对象」。
- 备选方案：
  - 手动勾选成员：多一步操作且容易漏；否决。
  - 只在创建时分组：无法表达后续整理；否决。
- 后果：`groups` 增加 `color` 列，`SCHEMA_VERSION` 升到 2；拖动结束需要额外计算空间归属；取色器使用 Ant Design `ColorPicker`，初始包体增大。

### ADR-018 自定义右键菜单追加 Windows 原生 Shell 菜单

- 状态：accepted
- 日期：2026-10-25
- 背景：项目自身的右键菜单只覆盖打开、定位、标注、属性、删除等操作；用户在资源管理器里常用的 WinRAR、Git、电脑管家等 Shell 扩展无法从画布触发。
- 决策：文件/文件夹/快捷方式的右键菜单底部追加「系统右键菜单…」；点击后由 Rust 在主线程用 `IContextMenu` + `TrackPopupMenuEx` 弹出 Windows 原生菜单，保留第三方扩展；菜单坐标由 `ClientToScreen` 从窗口内坐标换算。自定义菜单过长时在容器内滚动，不把系统菜单项硬塞进 HTML 菜单。
- 备选方案：
  - 在 HTML 菜单里复刻系统菜单项：无法覆盖未知第三方扩展，且需要维护命令映射；否决。
  - 直接把原生菜单当作唯一右键菜单：失去项目自身操作与统一主题外观；否决。
- 后果：`TrackPopupMenuEx` 会运行模态消息循环，必须放到窗口所属主线程（`run_on_main_thread`）；新增 `show_system_menu` IPC 与 `Win32_UI_Shell` / `Win32_UI_Shell_Common` feature。

### ADR-019 画布不重叠、对齐吸附与空间自动整理

- 状态：accepted
- 日期：2026-10-25
- 背景：自由摆放会让对象相互压住、空间彼此覆盖；多个对象只能靠鼠标手工对齐，整理成本高。
- 决策：节点之间、空间之间至少保留 8px 间距；空间是容纳成员的容器，成员位于空间内不算重叠。**空间框随成员自动扩缩**：成员集合或展示高度变化（拖入/拖出/删除/标注增删/文字改名换行）后，按成员包围盒 + 顶部标题区（32px）与四周内边距（16px）贴合空间框，与自动整理同一套尺度；空空间保持现状作为可拖入的容器；贴合只重算受影响的空间，尺寸未变时保持原引用。对象拖动过程中不校验碰撞：按下第一帧记录初始位置，拖动期纯跟随指针并做对齐吸附（把移动集合的边线与附近对象比对，6 屏幕像素内吸附并绘制虚线参考线；吸附目标与落点判定都走 rbush 空间索引的局部查询，O(log N)，不逐帧扫描全量对象——10 万对象时全量碰撞扫描会让主线程饱和，表现为卡顿与「拖不动」）。松手时用 rbush 一次性判定落点：吸附落点被非移动对象压住则退回拖动前的裸偏移，裸偏移仍被压住才整体回退。**空间拖动与对象拖动完全一致**：拖动期不校验碰撞、rbush 局部对齐吸附（其他空间参与吸附），松手统一判定落点——非成员对象与其他空间为障碍，成员随空间移动不参与判定，被压住先退回裸偏移、仍被压住整体回退；成员在按下时快照为排除集合。新建与导入对象用螺旋搜索整体平移到最近空位；空间右键「自动整理空间」按当前阅读顺序（先上后下、先左后右）排成网格并收高空间，若压到其他空间或非成员对象则整体让位。
- 备选方案：
  - 拖动全程逐帧碰撞校验：10 万对象下每帧 O(N) 扫描导致严重卡顿，且起始位置被压住时对象「拖不动」；已被本轮否决（即旧行为）。
  - 挤开其他对象（物理推挤）：会移动用户未选中的对象，结果不可预期；否决。
  - 自动整理按创建顺序：与屏幕上的阅读顺序不一致，整理后反而难找；否决。
  - 落点被压住时螺旋搜索就近空位：与拖动意图偏差不可预期，回退更可解释；暂不做，保留回退语义。
  - 空间拖动保留逐步碰撞约束（吸附 + 单轴滑动）：与对象拖动行为不一致，密集画布上表现为空间「推不动」；已在本轮统一为「拖动期不校验、松手判定」后否决（旧行为）。
  - 拖动成员期间逐帧跟随扩缩空间框：拖动一帧一个框尺寸，与吸附/落点约束相互干扰；只在松手提交后一次性贴合。
  - 空间贴合后与其他空间/对象重叠时整体让位：扩缩是成员变化的被动结果，自动搬动整个空间会让成员位置跳变；接受贴合后可能短暂重叠，由后续拖动/整理收敛。
- 后果：布局逻辑集中在 `client/domain/layout.ts`；历史数据若已重叠，拖动时忽略当前已压住的障碍，避免对象被永久卡死；自动整理进入单步撤销；拖动期不再有碰撞反馈，重叠只能在松手后被纠正（表现为退回原位），这是为 10 万对象性能接受的取舍。~~空间框不再有「手工留白」——框始终贴合内容，用户无法在空间内预留空位~~（该结论已被 ADR-023 部分推翻：允许手动放大框，但成员变化时仍按内容自动贴合）。

### ADR-021 大规模画布性能架构：拖动视觉直驱与一次性提交

- 状态：accepted
- 日期：2026-10-25
- 背景：10 万对象下拖动明显卡顿、空间「拖不动」、选中响应慢。确诊的根因都在 JS 侧而非渲染侧：① 空间拖动每帧把位移提交回 React 状态（全量 `setNodes` 映射 + 重渲染），每帧 O(N)；② 节点拖动每帧 `stage.find('Arrow')` 遍历全部图形并对每条箭头做 `edges.find`，万级连线时是每帧百万次比较；③ 每次状态变化（含选中）重建 10 万条搜索条目（含拼音转换）并对全量节点做迷你地图抽样 filter；④ 可见节点裁剪每帧对全量数组 filter；⑤ `Math.min(...nodes.map())` 在 10 万参数下超出调用栈。Konva 的 Canvas2D 绘制本身由 WebView2/Skia 走 GPU 合成，且只渲染视口内的对象，瓶颈不在显卡。
- 决策：拖动一律「视觉直驱 + 松手一次性提交」——拖动期直接驱动 Konva 图形位置（节点/空间框/空间标题/受影响箭头），不触碰 React 状态；松手时统一做落点判定并一次性提交。连线跟随用「节点 → 连线」倒排索引，每帧只更新受影响的箭头几何，不再 `stage.find` 全量遍历。图元组件（`NodeShape` / `GroupShape` / `EdgeLayer`）用 `React.memo` 包装，配合稳定的 tokens 与经 ref 转发的事件处理器，选中/平移等无关重渲染只影响真正变化的图形。搜索条目懒构建（空查询不构建全量条目）+ 预归一化（每键只做字符串比较）+ 拼音缓存空闲分批预热 + top-9 线性选择（省掉全量排序）。可见节点直接映射 rbush 命中项（O(命中数)），连线同样按视口裁剪（端点包络盒判定，缩小画布时视口覆盖全部、关系网仍完整）。迷你地图分布图改为单 canvas 绘制（对象点/空间框只在场景变化时重绘，平移只更新视口框 DOM）。大数组的 `Math.min(...map)` 展开全部改为单次循环。**超大选择集（>2000）拖动降级**：不逐个驱动图形与连线，只移动一个包围盒 ghost（视觉直驱），松手按整体包围盒做一次落点判定后一次提交。构建期手动分包：antd / pinyin-pro / konva+rbush 拆独立 chunk，首屏主脚本从 1.7MB 降到约 310KB。
- 备选方案：
  - WebGL 渲染器（PixiJS 等）替换 Konva：视口裁剪后同屏绘制量与总数量无关，Canvas2D 不是瓶颈；整层重写收益不成比例；否决。
  - 拖动期暂停 React 提交但保留逐帧全量计算：计算本身仍是 O(N)；否决。
  - 状态层换不可变增量结构（immer 等）：改动面大，当前一次性提交成本可接受；暂不做。
- 后果：渲染成本与对象总数解耦，同屏量只取决于视口；剩余 O(N) 成本都是「每次提交一次性」的（节点数组映射、防抖持久化；rbush 全量重建已由后续的常驻增量索引消除），10 万级表现为落点/删除后的短暂停顿而非持续卡顿。百万级需要批量持久化评估（见待复核）。空间拖动期不再逐帧重算成员归属，归属在松手提交时统一更新。

### ADR-022 持久化性能：读写分离连接、增量保存与空闲调度

- 状态：accepted
- 日期：2026-10-25
- 背景：10 万画布下卡顿的一部分不在视图层而在 SQLite：单连接被 `Mutex` 串行化，`scene_save` 每次全量 upsert 约 20 万行（refs + nodes）并持有写锁数秒，期间任何读取（缩略图、配置、单节点）都在排队，表现为「操作撞在一起锁事务」；启动全量引用校验（250 批 × 每批一个事务）与初始交互竞争；每张可见缩略图都为读 path/thumb_key 锁一次库；`synchronous=FULL` 每次提交 fsync；edges 与 annotation_targets 缺少清理语句需要的索引。
- 决策：① 读写分离——写连接保持 `Mutex` 串行，新增同一 WAL 文件的独立只读连接，场景加载/配置/单节点/缩略图元信息读走读连接，读不等待写事务提交；场景数据一次性拿完，操作过程中不按需查库。② 增量保存——`scene_save` 先读现有 `nodes` / `refs` 可变字段指纹（HashMap 对比），只 upsert 真正变化的行，10 万画布的常规保存从约 20 万次 upsert 降到个位数；groups/edges/annotations 数量级小，保持全量 upsert。③ 写只发生在操作结束之后——前端 350ms 防抖保存；启动引用校验按 `requestIdleCallback` 空闲分批（每批 400 个短事务，批间等待空闲帧），不与拖动/平移等视图操作同时进行。④ 缩略图元信息进程内缓存（path/is_exists/thumb_key，含「无缩略图」结论），每节点只查一次库，缓存文件命中完全不碰数据库；重关联/引用校验/迁移/重建后按 id 或整体失效。⑤ 连接调优：`synchronous=NORMAL`（WAL 下安全）、`temp_store=MEMORY`、`cache_size=-8000`、`mmap_size=256MB`。⑥ 索引：`edges(from_node)`、`edges(to_node)`、`annotation_targets(node_id)`（schema v3），支撑保存时的悬空边/标注目标清理。⑦ 序列化出主线程——保存时场景先在前端 Web Worker 里 `JSON.stringify`（`sceneSerialize.worker.ts`，不可用时回退主线程），Rust 侧 `scene_save` 接收 JSON 字符串并解析。⑧ 重命令异步化——`scene_load` / `scene_save` / `import_paths` / `ref_check` / `thumb_get` 改为 async 命令并在 `spawn_blocking` 线程池里查询/解析/写库/做文件 IO，主线程（UI 与窗口消息循环）永不被数据库与大 JSON 阻塞。⑨ 传输层增量——前端在 `tauri-api` 按对象引用对比上次成功保存的基线自动求差（不可变更新保证未变对象引用不变，diff 无遗漏），常规保存只序列化/传输变化与显式删除的行（`scene_save_delta`，量级通常是个位数对象，直接主线程 stringify）；每 20 次保存与失败后的首存强制全量对账，Rust 增量写库后对 refs/悬空边/标注目标做兜底清理（仅在真有删除时执行）。
- 备选方案：
  - 多写连接连接池：SQLite 单写者模型下只会互相 `busy`；否决。
  - 前端按修改事件维护差异语义（事件级增量）：所有命令都要维护差异语义，遗漏即数据漂移；已改为「保存时按对象引用对比快照自动求差 + 每 20 次与失败后首存全量对账 + Rust 侧悬空兜底清理」的快照 diff 方案——diff 在 `tauri-api` 一处集中、命令层无感知，且引用级对比保证无遗漏。
  - 保存时跳过 keep 清理段：删除的对象无法从库中清掉；保留，靠内存临时表 + 索引加速。
  - 后台线程保存（脱离主线程）：Tauri 命令本就运行在非主线程池；瓶颈在 SQLite 写事务本身，已由增量保存解决。
- 后果：交互期间的数据库争用基本消失——读不等写、写事务毫秒级；保存仍在防抖后同步序进行，极端连续操作下最坏延迟一个防抖周期。指纹对比使常规保存只写变化行，但首次保存（10 万行指纹读取）与全量导入仍是完整写入。`updated_at` 仅在行真正变化时更新，不再每次保存刷新全表。

### ADR-023 空间容器接纳与手动调框

- 状态：accepted
- 日期：2026-10-25
- 背景：对象拖出空间后无法再拖回——落点判定把「压住空间内既有成员」当成失败，整次拖动回退；同时空间框只能随内容被动扩缩，用户无法预留放入位置。
- 决策：
  - 落点在空间内即视为容器接纳：松手判定跳过该对象与空间内对象的碰撞检查，入库后按阅读顺序自动整理该空间成员，消解重叠；空间外落点仍按不重叠规则判定。
  - 选中空间显示四角手柄，拖动只改框的 `x/y/w/h`（最小 140×100），成员位置不动；手动尺寸不新增持久化字段，成员下一次变化（拖入/拖出/删除/标注）时仍由 `fitGroupToMembers` 按内容重新贴合。
- 备选方案：
  - 拖入时保留碰撞判定、失败后提示用户「先整理」：用户已完成拖动却得到失败反馈，且整理本身也要手动触发；否决。
  - 拖入成功后仅贴合并保留原始落点：成员仍互相压住，需要用户再次整理；否决。
  - 手动尺寸写独立字段并在自动化时保留外扩留白：框尺寸出现「手动/自动」双来源，成员变化后框可能突然跳回旧留白，语义不可解释；否决。
  - 拖框时同步缩放成员：用户只想扩大容器，成员变大会破坏网格与既有尺寸；否决。
- 后果：拖入空间的成功判定不再依赖空间内剩余空位；成员拖入后位置会被整理（不是落点原样），这是容器语义的必然结果。手动调框只是临时视图，成员一变就回到内容贴合尺寸。

### ADR-025 富文本卡片：wangEditor-next + HTML 存 `body`

- 状态：accepted
- 日期：2026-10-26
- 背景：用户需要「类似知识库的文章书写」能力，明确要求用国内的王富文本；画布上已有纯文本卡片（`kind=text`、`body` 存纯文本），需要在同一套场景模型、持久化与搜索链路里增加富文本，且不能让首屏包体被编辑器拖大。

  - 存进 `data_json`：该列已声明为「扩展样式 JSON」并在属性面板做 JSON 校验，塞 HTML 会破坏该契约；否决。
- 后果：新增两个前端依赖与一个懒加载 chunk（约 634KB，gzip 199KB），首屏主脚本基本不变；`rich` 图标需同时加进 `SystemIcon` 与画布图标预加载表；搜索与悬停提示必须避开 HTML，改为读 `subtitle`；`pnpm` 因 `es5-ext`（wangEditor 传递依赖）的 postinstall 触发 `strictDepBuilds` 报错，需在 `pnpm-workspace.yaml` 的 `allowBuilds` 中显式拒绝该脚本。

### ADR-026 原文件拖出与复制：只传引用、只声明 COPY

- 状态：accepted
- 日期：2026-10-26
- 背景：用户需要把画布上的项目文件夹直接拖进 IDE（VS Code 等）打开项目，而不必回资源管理器逐层找路径；「复制」也要能拿到原地址。既有画布行为里左键拖拽用于画布内移动，不能直接让位给系统拖放；同时 HC-12 要求绝不修改用户文件。
- 决策：手势用 `Ctrl + 左键拖拽`（位移超过 4px 才真正发起，避免 Ctrl 点击误触发一次落在自身窗口上的空拖放）；普通左键拖拽仍是画布内移动。Rust 侧新增两个命令：`copy_ref_files`（`clipboard-win` 写 `CF_HDROP`，入口为 `Ctrl+C` 与右键「复制文件」）、`drag_out_refs`（自研最小 `IDataObject` + `IDropSource`，主线程 `DoDragDrop`，数据对象只提供 `CF_HDROP` 与 `CFSTR_PREFERREDDROPEFFECT=COPY`，格式枚举只列这两种）。前端只传 `nodeId`，路径全部由 Rust 查库解析并校验存在性；文字、富文本、链接无原文件，不参与。为此把 `Ctrl` 从「追加选择」的修饰键中去掉（文档一直只写 `Shift` 追加选择）。
- 备选方案：
  - 引入社区 crate（`drag` / `tauri-plugin-drag`）：代码量更少，但引入非官方维护依赖，且核心行为（只 COPY、只导出显式引用）仍要自己兜；用户已选择自研；否决。
  - 用 `tauri-plugin-fs` 的 drag 能力或 WebView 的 HTML5 dragstart：WebView 无法给出 `CF_HDROP`，外部程序拿不到文件；否决。
  - 直接把「左键拖拽」改成系统拖出：破坏画布内移动这一最高频操作；否决。
  - 用 `IDragSourceHelper` 提供文件缩略图拖影：观感更好，但要再实现一层 Shell 帮助对象，本轮只保留系统默认拖放光标；暂不做。
- 后果：新增 windows feature（`Win32_System_Ole`、`Win32_System_Memory`、`Win32_System_DataExchange`、`Win32_System_Com_StructuredStorage`、`Win32_System_SystemServices`）与 `windows-core`（windows-rs 官方组成部分，非第三方）；`DoDragDrop` 会跑模态循环，只能派发到主线程，命令立即返回、错误只写 stderr；拖出示意（光标）依赖系统默认样式；`Ctrl` 不再能追加选择。

### ADR-028 文字/富文本改为弹窗编辑（推翻画布内联编辑）

- 状态：accepted
- 日期：2026-10-26
- 背景：文字卡片此前在画布上原地编辑（`CanvasTextEditor`，跟随视口的绝对定位 textarea）。用户反馈希望改回弹窗编辑：内联编辑区受缩放与视口变换影响、长文难以核对，且与随后加入的富文本编辑器无法共用同一套编辑体验。

### ADR-029 富文本媒体本地化：Raw IPC 二进制直传 + `richasset` 协议回读

- 状态：accepted
- 日期：2026-10-27
- 背景：v0.1.1 富文本只有格式化文字，用户要求支持插入图片与视频。wangEditor 默认的上传配置需要服务端、网络图片入口要发起外网请求，都违反 HC-13（纯本地、无外部请求）；base64 内嵌 HTML 会把正文体积放大 1/3 以上并撑爆数据库行，用户明确否决。
- 决策：
  - 上传走 Tauri 2 Raw IPC 二进制直传：`invoke('save_rich_asset', Uint8Array)`，body = `[ext_len: u8][ext ascii][文件字节]`，JSON 体直接拒绝；命令只收字节与扩展名，文件名由 Rust 生成 UUID（HC-12）。
  - 落盘复用 `assets/` 目录（启动时 `create_dir_all` 保证存在），扩展名白名单 png/jpg/jpeg/webp/gif/bmp/mp4/webm/ogg，图片 ≤20MB、视频 ≤100MB；HTML 只存 `assets/<文件名>` 相对引用，工作空间迁移后无需改写。
  - 回读走自定义 `richasset` 协议（`http://richasset.localhost/<文件名>`）：MIME 按扩展名映射，支持 HTTP Range 206 分片供视频拖动进度条；文件名严格校验（拒绝分隔符/`..`/`%`/白名单外扩展名）防目录穿越。
  - 上传大小与非空校验在前端和 Rust 边界同时执行；兼容 Windows BMP 的 `image/x-ms-bmp` MIME。媒体读写解析真实路径，资产目录不得越出当前工作空间，回读文件不得越出资产目录；协议保留完整路径供校验，不丢弃目录段。
  - 仅含本地图片/视频的富文本也允许保存，纯文本投影保持为空，卡片名称回退「富文本媒体」；真正空白的正文仍不覆盖原内容。
  - 编辑器移除「网络图片 / 网络视频」入口（`excludeKeys: ['insertImage', 'insertVideo']`）；粘贴截图自动进入 `uploadImage.customUpload`，即剪贴板/粘贴上传通道。
- 备选方案：
  - base64 data URL 内嵌 HTML：体积爆炸、保存传输量放大、数据库行膨胀；否决（用户明确要求文件方式）。
  - assetProtocol scope 配置 + 绝对路径：要把资产目录开进 scope，且 HTML 里存绝对路径，迁移工作空间后全部失效；否决。
  - 复用 `save_clipboard_image`（base64 参数）：与「不经 base64」的文件上传要求冲突；否决。
- 后果：新增 `save_rich_asset` 命令与 `richasset` 协议 handler（写盘走 `spawn_blocking`，不阻塞主线程）；删除富文本节点不回收 assets 里的媒体文件（与截图副本行为一致，有真实需求时再做 GC）；`dataWorkSpace/assets/` 从此承载截图副本与富文本媒体两类本地资产。

### ADR-030 保存链路：关窗先落库、Ctrl+S 立即保存、状态栏反映真实结果

- 状态：accepted
- 日期：2026-10-28
- 背景：保存是 350ms 防抖 + 关闭按钮直接 `close()`。改完最后一笔就关窗（或在防抖窗口内关机）会静默丢数据；状态栏的「已保存」是写死的字符串，保存失败时仍然显示已保存，等于误导用户。
- 决策：
  - 关窗拦截 `tauri://close-requested`：先 `preventDefault`，`await` 一次强制落库（绕过去抖），成功后再 `close()`；保存失败则**不放行**并提示原因，宁可让用户重试也不静默丢数据。第二次进入处理器时 `closing` 标记已置位，直接放行，避免死循环。
  - `flush` 与防抖保存共用同一个 `saveNow`；`saveNow` 在 `hydrated` 之前直接返回——未加载完就写库会把空场景落盘，等价清库。
  - 保存状态由 IPC 层通过订阅广播（`idle/saving/saved/error`），状态栏据此显示三态；失败同时有 `message.error`。
  - `Ctrl+S` 在主窗口触发立即落库（不改变选中与弹窗）；文字/富文本弹窗内 `Ctrl+S` 就地保存且不关闭，「保存」按钮才关闭；标注编辑框 `Ctrl+S`（或 `Ctrl+Enter`）保存标注、面板不关闭。
  - 文字/富文本弹窗取消时若有未保存改动，先弹二次确认，避免整篇内容被 Esc 抹掉。富文本的「是否有改动」由编辑器 `change` 事件标记，不比对 HTML 字符串（编辑器会规范化初始 HTML，字符串比对必然误判）。
- 备选方案：
  - 关闭前不 flush，只把防抖缩到 0：写库频率随交互飙升，10 万对象下会拖慢松手；否决。
  - Rust 侧退出时落库：场景在 WebView 内存里，Rust 拿不到；否决。
  - 关窗失败也放行：用户以为保存成功，实际丢数据；否决。
- 后果：关闭窗口最多多等一次写库（通常 <50ms）；`useScenePersistence` 同时负责加载、防抖、flush 与关窗守卫，成为保存链路的唯一入口。JS 侧 `onCloseRequested` 的默认实现是「处理器返回后若未 preventDefault，则调用 `destroy()`」，因此能力清单补了 `core:window:allow-destroy`。保存失败时保持窗口打开（已 preventDefault、不再调用 close），用户处理后重试即可。

### ADR-031 空间整理：只在进出空间时整理，组内重叠只推开被拖对象

- 状态：accepted（部分取代 ADR-019 的「拖入即整理」与 ADR-023 的「落点在空间内即整理」）
- 日期：2026-10-28
- 背景：此前任何一次「拖入空间」或「空间内拖动后压到成员」都会把整个空间按网格重排。用户在空间里手工摆好的布局会被一次微调冲掉，而且当时撤销栈只覆盖删除/整理，动作不可逆。
- 决策：
  - 只有 `groupId` 发生变化的对象（进出空间）才触发该空间的网格整理；这是结构变化，整理一次符合预期。
  - 空间内部拖动压到其他成员时，只用螺旋搜索把**被拖的那一个**对象推到最近空位，其余成员位置不动。
  - 网格整理仍是显式动作：右键「自动整理空间」随时可手动触发。
  - 所有改动坐标/结构的命令（移动、微调、改色、改名、连线、标注、导入、整理、删除）统一写入撤销栈，上限 30 步，`Ctrl+Z` / `Ctrl+Shift+Z`（或 `Ctrl+Y`）往返；方向键微调按 800ms 合并成一步。
- 备选方案：
  - 保留「拖入即全量整理」并补撤销：可用但动作仍然粗鲁，手摆布局每次都被打乱；否决。
  - 落点在空间内压住成员就拒绝放入：空间作为容器的接纳语义会丢失（ADR-023）；否决。
- 后果：空间成员位置由用户主导，只有进出空间才归整；`moveNodes` 不再做全组重排，10 万对象下也少了一次全组映射。

### ADR-032 首屏紧凑索引与正文按需加载（保存用 COALESCE 保护）

- 状态：accepted
- 日期：2026-10-28
- 背景：`scene_load` 一次返回全部节点，含 `body`（富文本 HTML，单条可达数万字符）。spec/02 早已写明「首屏只加载紧凑索引、详情按需拉取」，实现却一直是全量；正文越多，首屏越慢、内存越占。
- 决策：
  - 新增 `NODE_SELECT_BRIEF`：字段顺序不变，`body` 直接给 `NULL`；`node_body(id)` 单独取正文。
  - 保存侧把 upsert 的 `body = excluded.body` 改为 `COALESCE(excluded.body, nodes.body)`：正文「未加载」与「空正文」在协议上无法区分，用 COALESCE 保证未加载时不会把库里的正文写成 NULL。正文按设计不可清空（空内容视为放弃修改），所以不需要「显式清空」通道。
  - 前端打开文字/富文本弹窗、内容管理导出前先 `nodeBody`；搜索与悬停提示改用 `subtitle`（纯文本投影，本就是同一份内容）。
  - `db::tests` 增加两条回归：未加载正文的节点被移动后正文仍在；显式带正文时能覆盖。
- 备选方案：
  - 分页加载节点（每次 5000）：IPC 往返变多、峰值内存不变，收益不抵复杂度；否决。
  - 正文存单独表：能按需查询，但要多一次迁移与两张表的关联维护；当前规模不需要；否决。
  - 加 `bodyLoaded` 布尔字段：协议多一个只为一处服务的字段；COALESCE 已够；否决。
- 后果：首屏不再传输正文；代价是「弹窗打开」多一次往返（本机 IPC，通常 <5ms）。若将来允许清空正文，必须补 `bodyLoaded` 或显式 null 语义。

### ADR-033 导入分批提交：进度事件与可取消

- 状态：accepted
- 日期：2026-10-28
- 背景：`coding-conventions` §5 要求批量任务提供「进度、当前项、可取消」，但导入是「一个命令一次事务」，拖 3000 个文件时前端只能干等，界面像卡死，也无法中止。
- 决策：
  - Rust 侧改为 `import_paths_with_progress`：每 20 项一个事务并提交；批间调用进度回调（已处理/总数/当前项），并检查取消标记。
  - 取消标记放进程级 `IMPORT_JOBS`（`jobId → AtomicBool`），`cancel_import` 置位；不放 `AppState`，避免测试夹具跟着改。
  - 命令通过 `app.emit("import://progress", …)` 推送，前端 `listen` 后画左下角进度条；取消后返回 `cancelled: true`，界面提示「已处理 N 项，其余未导入」。
  - 失败项仍是「路径 + 原因」逐条返回（HC-14）。
- 备选方案：
  - 单个事务跑完再返回：取消就只能整批回滚，用户白等；否决。
  - 前端切批循环调用导入命令：每批都要重新做去重查询与放置计算，网格位置会错乱；否决。
- 后果：导入过程可能留下「部分完成」的状态，这是显式且可解释的（进度条 + 取消提示）；批内取消只保证已提交批次不丢，不会回滚。

### ADR-034 空间折叠与左侧大纲树

- 状态：accepted
- 日期：2026-10-28
- 背景：画布变大后「找不到东西」成了主要痛点：全靠缩放与迷你地图，缺少结构化的第二视角。空间越多，越需要把不相关的收起来。
- 决策：
  - `groups.collapsed`（v4 迁移，默认 0）：折叠后只画标题条（26px）、隐藏成员、不参与命中；`x/y/w/h` 不变，展开即恢复原样。
  - 折叠是视图状态但会持久化；**不进撤销栈**（否则 Ctrl+Z 会莫名其妙展开空间）。
  - 新增 `groupDisplayBox()`：折叠时返回标题条矩形，渲染、连线锚点、落点判定、适配画布、迷你地图统一用它，避免「看不见的框还在挡路」。
  - 折叠按钮放在标题行右端（`+` / `−`），与拖拽、重命名互不抢事件；折叠时不提供四角调框。
  - 左侧大纲树按空间分组，空间可逐个展开/收起（另有全部展开/收起）；树只导航不改数据，展开状态不持久化。
- 备选方案：
  - 折叠时也把成员藏进另一个图层但保留命中：视觉与命中不一致，误拖会选中看不见的对象；否决。
  - 用多画布隔离不同项目：用户明确不做多画布；否决。
- 后果：折叠空间的成员在画布上不可点，定位到它时画布会居中但成员仍隐藏，需要用户展开空间；若后续觉得别扭，可改为「定位即展开」（已记入待复核）。

### ADR-035 内容管理页与文本/富文本导出

- 状态：accepted
- 日期：2026-10-28
- 背景：文字与富文本是应用内内容，散落在画布上，找不全也带不走。用户明确「导图画布没意义，但文字/富文本要能导出」，并要求一个可视的管理页。
- 决策：
  - 顶部齿轮拆成「系统设置 / 内容管理」两个入口（原设置面板不变）。
  - 内容管理列出全部 `text` / `richtext`：标题、类型、所属空间、字符数（用纯文本投影长度，不加载正文）、操作（定位/编辑/导出/删除），顶部可按标题与正文片段筛选、可「导出全部」。
  - 「移动到空间」用下拉选择，落点排在空间内容末尾（最下方、按内边距左对齐），并让新旧空间重新贴合。
  - 导出由 Rust `export_contents` 执行：纯文本写 `.txt`；富文本写 `.html`，把 `assets/<文件>` 重写为同目录文件名并复制媒体本体，导出目录里直接双击可看。单条走「另存为」，批量走「选目录」，同名文件自动加 ` (2)` 后缀，不覆盖用户已有文件。
- 备选方案：
  - 富文本转 Markdown：需要 HTML→MD 转换器，表格/样式难以无损，转换质量不可控；否决（导出 HTML 保真）。
  - 把正文内嵌成 base64 的单个 HTML：体积膨胀且与工作空间资产重复；否决。
- 后果：导出目录里可能多出若干媒体文件，这是刻意设计（可单独取用）；`payload` 中的正文由前端按 ADR-032 先取回再随请求传入，Rust 不查库取正文。

### ADR-036 外部入口（热键/命令行/发送到）、目录监听与本地日志

- 状态：accepted
- 日期：2026-10-28
- 背景：工具想「随手用」，就不能要求用户先切到应用再拖文件；出错时也需要有现场可查——此前所有失败只有一闪而过的提示，用户反馈「导入失败」时开发手上没有任何信息。
- 决策：
  - 全局热键 `Ctrl+Alt+Space`（`tauri-plugin-global-shortcut`，在 Rust 侧注册）：唤起并聚焦窗口 + 广播 `shortcut://focus-search`，前端据此聚焦搜索框。注册失败只记日志。
  - 启动参数：**存在即导入**（`ploceus.exe <文件…>` 或 `--add <文件…>`）。首次启动排队等前端 `take_pending_imports` 取走；已在运行时由单实例回调把路径转交并广播 `import://external`。
  - NSIS 安装钩子把「络雀」写进「发送到」菜单（卸载删除），形成「右键 → 发送到 → 络雀」的入口。
  - 文件监听（`notify`）：只 watch 引用所在目录（`ref_dirs`），事件防抖 800ms 后做目录级增量校验（`ref_check_under_dirs`，只返回状态真正变化的条目），推 `refs://changed` 让卡片即时变为「缺失/恢复」。不做重命名猜测——两张卡片指到同一文件比「改了名要手动重连」更糟。
  - 本地日志：`dataWorkSpace/logs/app.log`，2MB 轮转一份备份；Rust 侧记录启动、导入/导出/保存结果与 panic；前端所有 IPC 失败经 `call` 上报 `log_write`。日志不出本机。
- 备选方案：
  - 用前端 JS 插件注册热键：需要额外 ACL 授权，且窗口 API 也在 JS 侧，跨进程时序更绕；否决。
  - 监听每个文件而不是目录：watch 数量与文件数同阶，10 万引用直接崩；否决。
  - 引入日志框架（tracing + appender）：依赖更重，当前只需要「一份可读的文本 + 轮转」；否决。
- 后果：`logs/` 进入工作空间（迁移与重建时一并处理），最大占用约 4MB；「发送到」只在安装版生效，便携运行需手动建快捷方式。

### ADR-037 每次需求更新与 bug 修复必升版本号（四处一致 + 发布日志）

- 状态：accepted
- 日期：2026-10-28
- 背景：此前版本号只在「发布」时才手工改，一批改动可以攒着不提版本；四个副本（`package.json`、`tauri.conf.json`、`Cargo.toml`、`Cargo.lock`）靠手改，漏一处就会出现「安装包版本 ≠ 界面版本 ≠ 发布记录」。一旦出现问题，无法从版本号判断线上那份代码包含哪些改动。
- 决策：
  - **版本号是改动的必带产物**：每次需求更新（新增或调整能力）与 bug 修复，都在同一批改动里提升版本号（`HC-17`）；修 bug / 小改动 patch，成批新能力 minor，架构级重写才 major。
  - **单一命令同步四处**：`pnpm version:bump patch|minor|major|<x.y.z>`（`scripts/bump-version.mjs`）。`Cargo.toml` 只改 `[package]` 段、`Cargo.lock` 只改 `ploceus-desktop` 条目，依赖的版本一律不动；发现某处与 `package.json` 不一致时直接报错，要求先对齐而不是悄悄覆盖。
  - **静态可查**：`pnpm check-spec` 新增 `HC-17` 检查——四处版本号必须相同；`release/log.md` 必须存在 `## v<当前版本>` 段落且至少一条改动说明。漏写日志与漏改副本会在提交前就红。
  - 版本号只在 `release/log.md` 写人话；提交信息不重复版本号，避免两处编号打架。
- 备选方案：
  - 只改 `package.json`、构建时注入其余三处：`Cargo.lock` 与 NSIS 产物名在构建期已固化，注入晚于读取，装出来的包名仍会错；否决。
  - 用 git hook 自动 bump：本项目明确不启用 git hooks（`docs/README.md` §6），且自动 bump 会在一次提交里堆多个版本号；否决。
  - 用日期版本号（`2026.10.28`）：与已有的 `0.1.x` 序列和 GitHub Releases 标签不兼容；否决。
- 后果：每批改动都会产生一个新版本号，安装包数量增长快于功能数量——这是有意的，版本号从此等于「一次可复现的代码状态」。`check-spec` 会让「改了代码没 bump」在提交前失败；临时调试可本地改代码不提交，但提交前必须补上。

### ADR-038 自动更新：官方 updater + minisign 验签（取代「v1 不启用自动更新」）

- 状态：accepted
- 日期：2026-10-30
- 背景：应用已经迭代到 `0.2.x`，每次发版都要让使用者手动下载安装包再覆盖安装。已有 Windows Authenticode 自签名证书，但它解决的是「这个 exe 是谁打的包」，且自签名不被系统信任；它不能用来判断下载到的更新包有没有被替换。
- 决策：
  - 用 `tauri-plugin-updater` + `tauri-plugin-process`，检查源是 GitHub Releases 的 `releases/latest/download/latest.json`（不计 API 限速，仓库为 public，无需 token）。
  - 更新包用 **minisign 密钥对**签名，公钥内置在 `desktop/tauri.conf.json` 的 `plugins.updater.pubkey`，私钥在 `desktop/signing/updater.key`（不入库，需离线备份）。验签失败不执行任何下载物。
  - 触发：启动后延迟 8s 自动检查，`app_meta.update_checked_at` 做 24h 节流；设置「关于」区可手动检查。自动检查失败只写日志，不打扰、不阻断启动。
  - 安装链路：下载（进度回调）→ **先 `flush()` 落库**（失败即中止）→ `install()` → `relaunch()`。安装会重启进程，这是唯一可能丢数据的环节，因此复用关窗前的保存守卫。
  - 发布：`pnpm release:publish` 生成 `latest.json` 并把安装包与同名 `.sig` 以 ASCII 名上传到对应 tag（Tauri 2 的 NSIS 更新产物就是安装包本体，下载地址直接指向 `.exe`）；`pnpm tauri:build` 由 `scripts/tauri-build.mjs` 注入签名私钥。
- 备选方案：
  - **自研「拉 GitHub API + 下载 exe + 静默安装」**：无需新密钥，但没有任何密码学校验（只能比同源的 SHA256，防不了篡改），且「退出进程 → 启动安装器 → 重启」的时序要自己处理，最容易出白屏/装不上；否决。
  - **自研 + 复用现有证书钉指纹（`WinVerifyTrust` + 比对签名者证书）**：不用新密钥，但要自己写 Win32 签名解析（含放行 `CERT_E_UNTRUSTEDROOT`），且证书换发即断更新通道；否决。
  - **改用 MSI 目标**：当前只发 NSIS，换 MSI 会推翻安装形态与「发送到」钩子；否决。
- 后果：多了一个必须长期保管的秘密（私钥或密码），丢失后已安装客户端只能手动重装一次；`0.3.0` 是第一个带更新能力的版本，必须手动装一次才能进入自动更新通道。发布多一步 `latest.json`，已由脚本自动化。Authenticode 签名与更新验签是两条独立链路，互不替代。
