# coding-conventions.md · 络雀编码约定

> 技术栈未定，本文件只固化与技术选型无关的约定；标「待补」的条目在选型确定后同批补齐，不预先猜测框架写法。

## 1. 语言与类型

- 采用严格类型检查；能静态约束的不用运行时兜底。
- 若最终选择 TypeScript：禁止 `any`（用 `unknown` + 类型守卫）；纯类型导入用 `import type`；`catch (e: unknown)` 后再收窄。
- 接口 / 数据结构必须显式声明类型，禁止靠推断传递跨层数据。
- 校验只在边界处（用户输入、文件系统返回、外部 API）；内部模块互信，不做冗余校验。

## 2. 命名

| 对象 | 规则 | 示例 |
| --- | --- | --- |
| 变量 / 函数 | camelCase | `buildPlan` |
| 类型 / 组件 | PascalCase | `OrganizePlan` |
| 页面 / 规则文件 | kebab-case | `organize-preview` |
| 常量 | UPPER_SNAKE_CASE | `MAX_SCAN_DEPTH` |
| 环境变量 | 全大写下划线 | `ORGANIZE_ROOT` |
| 数据结构主键 / 关联键 | 自定义 ID | `planId` / `fileId`，禁止依赖自增 |

- 命名表达职责而非实现：`buildPlan` 优于 `doOrganize2`。
- 同一概念全仓库同名，禁止「方案 / 计划 / plan / scheme」混用（术语统一见 [spec/00-overview.md](spec/00-overview.md)）。

## 3. 注释

- 一律简体中文；函数 / 模块顶部块注释说明**意图与边界**，行内细节用 `//`。
- 不为自明代码加注释；注释解释「为什么」，不复述「做什么」。
- 禁止 `TODO` / `FIXME` / `// removed ...` 占位注释：要么现在做，要么写进待决清单，要么不留。

## 4. 错误处理

- 文件操作错误必须携带「路径 + 操作 + 原因」三层信息，并按 HC-14 呈现给用户。
- 禁止空 `catch`、禁止只打日志不返回；失败要么重试（幂等前提下），要么上报。
- 用户可见错误用业务语言描述后果与下一步，不直接抛原始堆栈。

## 5. 批量任务与长任务

- 扫描、整理、撤销等批量任务必须提供：进度（已处理 / 总数）、当前文件、可取消。
- 批量执行前默认预演（dry-run），展示将受影响的文件数与路径范围，用户确认后才落地（HC-11）。
- 取消或中断后必须保持状态一致：要么按操作记录回滚，要么明确标记「部分完成」，不允许静默半成品（HC-10）。

## 6. 文件创建纪律

- 优先改已有文件；确需新建时才新建，并在同一批改动中更新 `project-overview.md`。
- 临时调试脚本文件名以 `_` 开头（如 `_scan-debug`），不入主流程，提交前删除。
- 不建空文件、空目录、空占位章节。

## 7. 缺陷修复三段式

修 Bug 前先用三行写清边界，防止「修好 A 顺手弄坏 B」：

```
现状：WHEN 对含 3000 个文件的目录执行按类型归档 THEN 界面无进度且无法中断（缺陷）
期望：WHEN 执行批量归档 THEN 显示进度与当前文件，且可随时取消（修复目标）
回归护栏：WHEN 中途取消 THEN 已处理文件与操作记录必须保持一致，不得丢失或重复（不可破坏的既有行为）
```

判断规则：这次修复**可能波及什么**，就为它写护栏；文件操作类修复必须覆盖「预演 / 执行 / 撤销」三条路径。
